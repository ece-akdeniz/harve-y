**What the runner does:**
- **Workers and coordinator:** each supplier thread has its own worker that asks `agent.propose(case, threads, sid)` for a move. Agents without `propose` fall back to an adapter around `decide`. The coordinator lock covers only the decision and the journal write, never an HTTP call. Every close (supplier agreed, wave cap, all threads done, or an agent close request) goes through `evaluator.close_decision`.
- **Rate limit and sessions:** one limiter per API key spaces calls evenly at 8 per second with no bursts. At most 10 sessions are open at once.
- **Journal:** each POST's move ID and payload go to `journal.jsonl` before sending, and retries reuse both.
  - An uncertain outcome or a 409 triggers a GET of the session and thread before anything else is sent.
  - A 422 is not retried; two in a row on one thread stop that thread.
  - A 429 for the practice limit stops new cases from starting.
- **Restart:** the runner resumes the session recorded in the journal, or the one named in a 409 "one session per case", and settles moves that never got an outcome. To resume a previous run, set `NEGOTIATOR_JOURNAL` to that run's journal file.
- **Deadlines:** each thread has a 60 s buyer window and a 35 s target for buyer work. A watchdog closes at max(90 s, slowest round + 15 s) before the wave cap. The final-wave poller updates the cap from fresh `seconds_left`.
- **Per-session send slot:** hosted answers parallel requests on one session slowly (about 16–18 s each instead of about 0.5 s). So the runner sends one request per session at a time, but stops waiting 25 s before a thread's own deadline and sends anyway.
- **Run config:** the trace's `run` event records the runner type, commit, parallel setting and all budgets.

**Tests:** the full suite passes (78 tests, ruff clean). The runner tests use the kit simulator on a sped-up clock with the 60-second rule on. They cover:
- supplier replies delayed 30–50 s with zero timeouts, with and without the send slot;
- a check that waiting serially for a 50 s reply costs a 409 late;
- a request still pending when a close happens;
- a stale offer at close, for both 409 and 422;
- restart from the journal with no duplicate session or move;
- a lost reply resolved by retrying with the same move ID;
